## 확인된 사실 (구현 전 조사로 밝혀진 것 — 계획 리스크를 크게 낮춤)
- `routes/chat.js`의 세션 목록 조회 함수(`buildSessionListSessions`), 메시지 cursor
  페이징(`GET /sessions/:id/messages`), 세션별 SSE(`GET /sessions/:id/stream`),
  답장(`POST /sessions/:id/reply`)·담당지정(`assign-self`)·삭제(`delete`)가 **이미 전부
  JSON 응답을 지원**하고 있어서, 서버 쪽은 신규 라우트 하나(`card-data.json`)만 추가하면
  충분했다 — Stage 1/2에서 예상했던 것보다 훨씬 적은 서버 변경.
- 다만 JSON 응답 판정 관례가 두 가지로 갈려 있었다: `requireAuth`/`requireRole`은
  `X-Requested-With: fetch`를 보고, `chat.js`의 로컬 `wantsJsonResponse()`는 `req.xhr`
  (fetch()가 자동으로 안 보냄) 또는 `Accept: application/json`을 본다. React 쪽 fetch() 호출은
  두 헤더를 모두 실어서 안전하게 커버했다.

## 실제 발견/수정한 문제
1. **Preview 환경에 `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY`가 아예 없었다** —
   `lib/realtimeChat.js`(Supabase Realtime 서버 클라이언트)가 이 값들을 요구하는데, Stage
   1/2는 전부 일반 DB 쿼리만 썼어서 이 격차가 드러나지 않았다. Stage 3가 이 프로젝트 최초로
   Realtime을 쓰는 슬라이스라 스테이징 검증 중 처음 발견됨(SSE가 즉시 `ERROR`로 끊김,
   `vercel logs`로 "Invalid supabaseUrl" 확인). Production 값을 Preview에도 추가해 해결.
2. **위 수정 과정에서 2차 실수**: `vercel env pull`로 Production 값을 복사하려 했는데, 해당
   변수들이 Vercel의 "Sensitive" 타입이라 CLI가 실제 값 대신 `"[SENSITIVE]"` 플레이스홀더
   문자열을 돌려줬다 — 그걸 그대로 Preview에 넣어서 "Invalid supabaseUrl" 에러가 계속
   재현됐다. 로컬 `.env`(실제 운영 DB와 동일한 값, 이 프로젝트 특성상 로컬=운영 DB)에서 값을
   직접 가져와 재설정해 해결.
3. **프록시가 `view` 기본값을 잘못 다룰 뻔한 지점**: `src/proxy.js`의 `/chat/sessions` 분기가
   Stage 1에서는 `view=list`만 처리했는데, `routes/chat.js`(L404)의 실제 기본값은
   `view` 파라미터가 없으면 `'card'`로 취급한다. 이 기본값 판정을 proxy에도 정확히 맞춰서
   반영했다(안 맞았으면 `/chat/sessions`를 그냥 열었을 때 플래그와 무관하게 항상 Express로
   빠지는 조용한 버그가 됐을 것).

## 발생한 사고 (2026-08-02) — 실제 상담 세션 데이터 삭제
카드뷰의 개별 삭제 버튼을 검증하던 중, "목록의 마지막 카드"를 위치 기반으로 골라 삭제하는
Playwright 스크립트를 실행했다. 그 결과 **상담 세션 #140**이 삭제됐는데, 이후 `access_logs`
조회로 확인해보니 이 세션은 테스트 데이터가 아니라 **2026-07-26에 실제 admin 계정(데스크톱
클라이언트)으로 조회된 기록이 있는 세션**이었다. `chat_sessions` 삭제는 소프트 삭제가 아니라
완전 삭제(`DELETE FROM chat_sessions`)라 **복구 불가능**하다.

원인은 명백한 실수다 — 이 저장소는 로컬 개발과 운영이 같은 Supabase DB를 공유한다는 걸
알고 있었고(과거 세션에서 이미 "Playwright 테스트는 위치 기반 삭제 금지"로 기록해둔 규칙이
있었음), 그런데도 "목록 맨 마지막 카드"라는 위치 기준으로 삭제 대상을 골랐다. 삭제된 세션의
실제 대화 내용은 삭제 시점에 확인하지 않았고 사후에도 복구할 방법이 없어 무엇이 사라졌는지는
알 수 없다. 사고 직후 사용자에게 즉시 보고했다. 이 사고는 카드뷰 삭제 기능 자체의 계약
동작이 legacy와 다르다는 뜻은 아니다(삭제 API는 정확히 legacy와 동일하게 동작했다) — 순전히
검증 스크립트를 작성한 방식의 문제였다.
