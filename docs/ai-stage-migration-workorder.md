# AI 단계별 전환 작업지시서 (Express + EJS -> 점진 전환)

## 0. 목적과 원칙
- 목적: 운영 중단 없이 UI/프론트 레이어를 점진적으로 현대화한다.
- 원칙: 전면 전환 금지, 단계별 전환만 허용한다.
- 원칙: 각 단계는 계약 테스트 + 스테이징 실사용 검증 + 롤백 경로 점검을 모두 통과해야 다음 단계로 이동한다.
- 원칙: 기존 Express 라우트, 세션/RBAC, DB 계약은 단계별로 유지한다.

## 0-2. 전환 완료 및 후속 결정 (2026-08-02)
Stage 1~3(계획된 전 범위)이 production에 순차 전환 완료됐다 — 상세 근거/검증 기록은
`docs/ai-stage-1-checklist.md`~`docs/ai-stage-3-checklist.md`의 "Production 전환" 절
참고. 이 문서가 정의한 단계는 3단계가 마지막이며, 이후 별도 Stage 4는 계획되어 있지
않다.

**레거시 EJS 폴백 경로 유지 결정**: 8개 플래그가 전부 production ON이라 지금은 legacy
Express+EJS 코드가 실제로는 안 타지만, 롤백 안전망으로 **당분간 삭제하지 않고
유지**하기로 결정했다(2026-08-02). 근거: (1) 플래그를 다시 끄면 즉시 legacy로
복귀하는 게 이 마이그레이션 전략의 핵심 안전장치였고, 코드를 지우면 이 안전장치가
사라진다. (2) 현재 실사용 트래픽 노출이 갓 시작된 시점이라 예상 못 한 회귀가 나타날
가능성이 아직 남아있다. (3) 유지 비용(저장소 크기, 약간의 혼란)이 낮다. legacy 코드
정리는 production 플래그가 안정적으로 유지된 지 충분한 시간이 지난 뒤, 별도 작업으로
재검토한다 — 지금 시점에 예정된 일정은 없다.

## 0-3. Stage 이후 후속 기능: 오더 상세페이지 수정 가능화 (2026-08-02)
Stage 1~3 완료 이후 별도로 요청된 기능 — `views/orders/detail.ejs`는 원래 순수 읽기전용
(관리자용 상태변경/기사배정/요금 미니폼 3개만 예외)이었는데, 이미 전환된 접수폼
(`OrderForm.js`, `/orders/new`)을 `mode="edit"`으로 확장 재사용해 오더 상세페이지
자체를 수정 가능하게 만들었다. 새 플래그 `NEXT_ORDER_DETAIL_EDIT_ENABLED`(Stage 번호
없음 — 워크오더 3단계는 이미 완료 처리됨)로 게이팅, production에 검증 후 ON. 신규
라우트는 `POST /orders/:id`(수정), `GET /orders/:id/data.json`,
`POST /orders/:id/admin-memo`(관리자 메모 단독) 3개뿐이고, 기존 `POST /:id/fare`와
`views/orders/detail.ejs`는 완전히 그대로 남겨 플래그 OFF 시 100% 기존 동작으로
롤백된다. 검증: 임시 Vercel Preview 배포로 prefill/저장/구간(order_legs) 배정 보존·
경유지 개수 변경 시 재생성/client 읽기전용/`/orders/new` create 모드 회귀 없음을
Playwright로 확인 → production 배포(플래그 OFF 상태로 먼저 반영해 legacy 무변경 확인)
→ 플래그 ON + 재배포 → 동일 시나리오를 production에서 재확인, 전부 통과.

## 1. 공통 운영 규칙
- 릴리스 단위: 단계 내에서도 화면/기능을 작은 배치로 분할 배포한다.
- 배포 전략: `git push origin main` → Vercel GitHub 연동 자동 배포 → 별칭(`b2bcarkr.vercel.app`)
  자동 전환 방식을 쓴다(수동 `vercel --prod` CLI 배포는 더 이상 기본 경로가 아니다). 검증 전
  변경은 별도 브랜치/PR 또는 기능 플래그 OFF 상태로 main에 반영해, main 반영 자체가 곧
  프로덕션 노출로 이어짐을 감안한다.
- 기능 플래그: 신규 UI는 플래그로 켜고 끈다. 기본값은 OFF.
- 데이터 계약: 요청/응답 스키마와 폼 필드명은 기존 계약을 유지한다.
- 마이그레이션: DB 변경은 최소화하고, 필요 시 앱 배포와 분리해 선적용/후적용 계획을 문서화한다.

## 7. 이 프로젝트 전용 주의사항
- 로컬 npm start 실패가 포트 충돌/권한/환경 영향일 수 있으므로, 코드 불량과 분리해서 판정한다.
- Supabase 마이그레이션 누락 시 런타임 오류가 발생할 수 있으므로, 앱 배포와 별도로 DB 반영 상태를 매번 확인한다.
  - 실사례(2026-07-29): `chat_sessions.user_hidden_at`, `ferry_fare_rules`가 코드엔 반영됐지만
    운영 DB엔 없어 `/orders/ai-intake`가 500을 낸 적이 있다. 배포 직후 핵심 화면 스모크
    테스트를 반드시 거친다.
- 예약일시/예약기준/요금/상담상태처럼 도메인 민감 필드는 UI 변경보다 데이터 계약 검증을 우선한다.
- 운영 DB에 대한 스키마 변경(ALTER/CREATE 등)은 자동화 도구가 직접 실행하지 못하도록 막혀
  있다 — 마이그레이션 SQL은 사용자가 Supabase SQL Editor 등에서 직접 실행하는 것을 기본
  경로로 삼고, 작업 순서는 "① 마이그레이션 SQL 사용자 실행/확인 → ② 코드 배포(git push)"
  순서를 지킨다(반대 순서로 배포하면 위 실사례처럼 운영 장애로 이어진다).
- 자동화 테스트/재현은 반드시 `qa_test_bot` 전용 계정으로 하고, admin 등 실사용 계정으로
  로그인하지 않는다(단일 활성 세션 정책 때문에 실사용자가 강제 로그아웃된다).
