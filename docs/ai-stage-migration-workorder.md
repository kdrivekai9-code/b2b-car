# AI 단계별 전환 작업지시서 (Express + EJS -> 점진 전환)

## 0. 목적과 원칙
- 목적: 운영 중단 없이 UI/프론트 레이어를 점진적으로 현대화한다.
- 원칙: 전면 전환 금지, 단계별 전환만 허용한다.
- 원칙: 각 단계는 계약 테스트 + 스테이징 실사용 검증 + 롤백 경로 점검을 모두 통과해야 다음 단계로 이동한다.
- 원칙: 기존 Express 라우트, 세션/RBAC, DB 계약은 단계별로 유지한다.

## 0-1. 현재 코드 상태 보정 (최종 갱신: 2026-07-29)
- AI 챗봇 화면은 단순 정적 화면이 아니라, 세션 유지/idle 판정/health 체크/최근 항목 삭제/상담 플로우가 결합된 운영 화면이다.
- 따라서 Next 전환 1단계의 우선 대상은 읽기 전용 대시보드/목록이며, AI 챗봇은 3단계에 가까운 고난도 영역으로 취급한다.
- 최근 항목 삭제는 사용자 화면 전용 숨김(user_hidden_at)이며, 관리 화면은 유지한다.
- AI health는 1분 주기 폴링이며, 실제 idle은 챗봇 입력 activity 기준으로 판정한다.
- 이 문서는 전환 순서/게이트를 정의하는 문서이고, 프레임워크 전환 자체를 이미 수행했다는 뜻은 아니다.
- **정정(2026-07-29)**: `ai-stage-migration-overview.md`/`ai-stage-execution-order.md`/
  `ai-stage-1~3-checklist.md`에 남아있던 "2026-07-27 PASS(판정자: GitHub Copilot)" 기록을
  전부 무효화하고 미착수 상태로 되돌렸다. 코드베이스에 Next.js/Vite 관련 구현·의존성·config가
  전혀 없고(package.json에 next/vite 미포함), 체크리스트 본문 항목이 전부 미체크 상태로
  남아있어 판정과 실제 산출물이 불일치했기 때문이다. 실제로는 **Next 전환이 아직 한 화면도
  시작되지 않은 상태**이며, 지금까지의 모든 변경은 기존 Express + EJS + vanilla JS 구조
  내에서 이루어졌다(AI 챗봇 오더유형 판별 규칙, 요금 계산 동기화, 말풍선 UI 등 — 전부 이
  세션에서 Express 라우트/EJS/정적 JS 파일을 직접 수정한 결과다). 앞으로 실제 전환 착수 시
  이 5개 문서를 함께 갱신해야 한다.
- **배포 방식 변경(2026-07-29)**: 기존에는 `npx vercel --prod`로 수동 CLI 배포 후 별칭을
  수동 전환했으나, 이제 Vercel 프로젝트가 GitHub 저장소(`kdrivekai9-code/b2b-car`)에
  연결되어(`vercel git connect`) `git push origin main`만으로 자동 프로덕션 배포 +
  별칭(`b2bcarkr.vercel.app`) 자동 전환이 이루어진다. 아래 "1. 공통 운영 규칙"의 배포 전략과
  "6. 배포/롤백 운영 템플릿"은 이 새 방식을 전제로 적용한다.
- **마이그레이션 드리프트 실사례(2026-07-29)**: 배포된 코드(`routes/orders.js`)가 참조하는
  `chat_sessions.user_hidden_at` 컬럼과 `ferry_fare_rules` 테이블이 실제 운영 Supabase DB에
  반영되지 않아 `/orders/ai-intake`가 500 에러를 냈다. 앱은 이미 배포됐는데 마이그레이션만
  누락된 전형적인 사례로, "7. 이 프로젝트 전용 주의사항"의 기존 경고가 실제로 발생한 것이다.
  운영 DB 스키마 변경은 이 세션에서는 자동 실행이 차단되어 있어(운영 DB 직접 변경은 사용자
  승인 후 사용자가 Supabase SQL Editor에서 직접 실행) 수동으로 반영했다 — Next 전환 단계에서
  DB 변경이 필요할 경우도 동일하게 "선적용 SQL을 사용자가 직접 실행 → 앱 배포" 순서로
  분리해야 한다.

## 1. 공통 운영 규칙
- 릴리스 단위: 단계 내에서도 화면/기능을 작은 배치로 분할 배포한다.
- 배포 전략: `git push origin main` → Vercel GitHub 연동 자동 배포 → 별칭(`b2bcarkr.vercel.app`)
  자동 전환 방식을 쓴다(수동 `vercel --prod` CLI 배포는 더 이상 기본 경로가 아니다). 검증 전
  변경은 별도 브랜치/PR 또는 기능 플래그 OFF 상태로 main에 반영해, main 반영 자체가 곧
  프로덕션 노출로 이어짐을 감안한다.
- 기능 플래그: 신규 UI는 플래그로 켜고 끈다. 기본값은 OFF.
- 데이터 계약: 요청/응답 스키마와 폼 필드명은 기존 계약을 유지한다.
- 마이그레이션: DB 변경은 최소화하고, 필요 시 앱 배포와 분리해 선적용/후적용 계획을 문서화한다.

## 7. 이 프로젝트 전용 주의사항
- 로컬 npm start 실패가 포트 충돌/권한/환경 영향일 수 있으므로, 코드 불량과 분리해서 판정한다.
- Supabase 마이그레이션 누락 시 런타임 오류가 발생할 수 있으므로, 앱 배포와 별도로 DB 반영 상태를 매번 확인한다.
  - 실사례(2026-07-29): `chat_sessions.user_hidden_at`, `ferry_fare_rules`가 코드엔 반영됐지만
    운영 DB엔 없어 `/orders/ai-intake`가 500을 낸 적이 있다. 배포 직후 핵심 화면 스모크
    테스트를 반드시 거친다.
- 예약일시/예약기준/요금/상담상태처럼 도메인 민감 필드는 UI 변경보다 데이터 계약 검증을 우선한다.
- 운영 DB에 대한 스키마 변경(ALTER/CREATE 등)은 자동화 도구가 직접 실행하지 못하도록 막혀
  있다 — 마이그레이션 SQL은 사용자가 Supabase SQL Editor 등에서 직접 실행하는 것을 기본
  경로로 삼고, 작업 순서는 "① 마이그레이션 SQL 사용자 실행/확인 → ② 코드 배포(git push)"
  순서를 지킨다(반대 순서로 배포하면 위 실사례처럼 운영 장애로 이어진다).
- 자동화 테스트/재현은 반드시 `qa_test_bot` 전용 계정으로 하고, admin 등 실사용 계정으로
  로그인하지 않는다(단일 활성 세션 정책 때문에 실사용자가 강제 로그아웃된다).
