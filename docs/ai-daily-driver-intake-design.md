# 일일기사(daily_driver_order) / 프리미엄(premium_order) AI 챗봇 접수 FSM 설계 (v2, 확정)

v1에서 올라온 질문 7개에 대한 답변을 반영해 확정한 버전. §8은 전부 "확인 필요"에서
"결정 사항"으로 바뀌었다.

## 0. 현재 상태 요약 (설계 전 확인된 사실)

- **의도 분류는 이미 3갈래로 나뉜다** (`lib/hybridChat.js`): `dispatch_order`(탁송) /
  `proxy_order`(대리, → **아래에서 "프리미엄"으로 개칭**) / `daily_driver_order`(일일기사).
  `routes/orders.js`의 `classifyOrderIntentByRule()`가 키워드로 LLM보다 우선 판정한다.
- **오더 타입이 DB에 저장되지 않는다.** `orders` 테이블에 타입 컬럼이 없다 —
  **→ 결정: `orders.order_type` 컬럼 신설, 값은 `dispatch`/`premium`/`daily_driver` 3종.**
- **경유지는 대화형으로는 1개까지만 지원된다** — 아래 §4에서 "추가할까요?" 루프로 확장.

## 1. 오더 타입 체계 (확정)

**3종, 프리미엄이 기본이고 일일기사는 그 하위 특수케이스.**

- `dispatch`(탁송) — 기존과 동일, 변경 없음.
- `premium`(프리미엄 서비스 예약) — **기존 `proxy_order`(대리)의 새 이름.** 이 앱의
  대리 서비스는 원래 법인 대상(법인대리 서비스)이라는 전제 그대로, 이름만 "프리미엄
  서비스 예약"으로 바꾼다. 대화 진입/필드수집 흐름은 지금 대리 흐름과 동일하되, §5의
  경유지 대기시간 질문이 새로 붙는다.
- `daily_driver`(일일기사) — 프리미엄의 세분화. 두 경로로 진입한다:
  1. **직접 진입**: 최초 메시지 자체가 일일기사 신호(`DAILY_DRIVER_WORDING_RE`, 8시간
     이상 문구 등)를 명확히 담고 있으면 처음부터 일일기사 전용 FSM(§2)으로 진입.
  2. **자동 승격**: 처음엔 프리미엄으로 접수됐지만 실제 소요시간이 8시간 이상으로
     확인되면 `premium` → `daily_driver`로 자동 전환(§7).

## 2. 일일기사 FSM — 응답 순서 및 필드

```
1. "안녕하세요. 일일기사 예약을 도와드리겠습니다."   ← 답변부터, FSM 진입 전
2. [필수] 왕복/편도 확인 — "이용 형태를 선택해 주세요\n1. 왕복  2. 편도"
3. FSM 시작
```

왕복 기준(편도는 §3 참고):

| 순서 | 필드 | 필수/선택 | 질문 방식 |
|---|---|---|---|
| 1 | trip_type (왕복/편도) | 필수 | 1/2 선택형, 최초 1회 |
| 2 | 예약일시 | 필수 | 기존 방식 동일 |
| 3 | 출발지 주소 | 필수 | 기존 방식 동일 |
| 4 | 출발지 연락처 | 필수 | 기존 방식 동일 |
| 5 | 차량번호 | 선택 | 기존 방식 동일("없어"로 스킵) |
| 6 | 경유지 (반복) | 선택 | §4 — "추가할까요?" 루프 |
| 7 | 경유지 대기시간 (경유지 있을 때만, 경유지별로 각각) | 선택 | §4 — **2단계 질문(있는지 → 얼마나)** |
| 8 | 도착지 주소 | 필수 | 기존 방식 동일. §5 골프장 특례 |
| 9 | 도착지 대기시간 | 선택 | §5 — **2단계 질문(있는지 → 얼마나)**, 골프장이면 질문 생략+기본 5시간 |
| 10 | 최종 목적지 | 필수(왕복만) | §3 |
| 11 | 기사전달사항 / 업체전달사항 | 선택 | §6 — 탁송과 동일 구분 + 요약 규칙 |

## 3. 편도(one-way)와의 차이

- **최종 목적지(10번) 항목이 아예 없음** — 질문 안 함, 필드 자체 미수집.
- 그 외 1~9, 11번은 왕복과 100% 동일.
- §5의 "도착지=골프장이면 대기시간 기본 5시간"은 **왕복에만 적용**. 편도는 골프장이어도
  자동 기본값 없이 9번 질문 흐름을 그대로 탄다.

## 4. 경유지 수집(반복) + 대기시간 — 2단계 질문 (수정됨)

- 경유지 주소를 하나 받을 때마다 "경유지를 더 추가하시겠어요?"로 추가 여부 확인 → 예면
  다음 경유지 주소를 다시 물음, 아니오면 다음 단계로.
- **대기시간은 경유지별로 각각, 2단계로 질문한다** (v1의 "능동적으로 안 물어봄" 방침을
  아래처럼 수정):
  1. "이 경유지에서 대기 시간이 있으신가요?" (있음/없음)
  2. 있으면 → "예상 대기시간을 알려주세요 (예: 60분, 잘모른다)" — 숫자 응답과 "잘모른다"
     둘 다 유효한 답으로 받고, 어느 쪽이든 접수를 막지 않는다.
- 도착지 대기시간(§5)과 완전히 같은 질문 패턴 — 경유지·도착지 구분 없이 "있는지 →
  있으면 얼마나"로 통일.

## 5. 도착지 대기시간 + 골프장 특례

- §4와 동일한 2단계 질문: "도착지에서 대기 시간이 있으신가요?" → 있으면 "예상
  대기시간을 알려주세요 (예: 60분, 잘모른다)".
- "없음"/"잘모른다"/무응답이어도 그 값 없이 접수를 계속 진행한다(블로킹 안 함).
- **왕복이고 도착지 주소에 골프장 신호가 있으면**, 이 질문 자체를 생략하고 대기시간을
  **기본값 5시간**으로 자동 등록한다(사용자가 이미 다른 값을 말했다면 그 값 우선).
- **골프장 판별 패턴 확대(결정)**: 문자열 `"골프장"` 단독 매칭 대신
  `/골프장|골프클럽|컨트리클럽|\bCC\b|\bGC\b/` 사용 — "OO CC"/"OO GC" 표기 포함.

## 6. 전달사항 (기사전달사항 / 업체전달사항)

- 탁송과 동일하게 두 갈래(`memo`/`billingMemo`)로 구분.
- **요약 규칙(신규, 일일기사·프리미엄 전용)**: 전달사항이 길거나 여러 건이면 원문 그대로
  붙이지 말고 핵심만 `항목 : 내용` 형식으로 정리:
  ```
  세차상태 : 이물질 확인 요망
  주차위치 : 지하 2층 B구역
  하차 시 : 시동 걸어둔 채 대기
  ```
- 탁송 프롬프트는 "원문 그대로" 규칙을 유지 — **결정(§7 하단): 일일기사/프리미엄 전용
  시스템 프롬프트를 탁송과 분리**하므로 이 요약 규칙은 그 전용 프롬프트에만 넣는다.

## 7. 프리미엄(premium) 오더 흐름 + 일일기사 자동 승격

### 7-1. 경유지 대기시간 질문 (프리미엄 전용)

프리미엄 오더에 경유지가 있으면:
1. "대기 시간이 있으신가요?" (없음 / 있음-정확히 모름 / 직접 입력도 인식)
2. **"없음"** → 일반 **법인요금서비스**(경유지 추가요금만 받는 기존 구간요금제)로 간주,
   종료.
3. **"있는데 정확히 모름"** → 총 기사 예약시간을 추가로 질문:
   `1. 4시간 이내  2. 8시간 이내  3. 8시간 이상`

### 7-2. 일일기사 자동 승격 판정 (결정된 우선순위)

주문이 `premium`으로 접수된 뒤, 아래 순서로 8시간 이상 여부를 판정해 `daily_driver`로
자동 전환한다:

1. **1순위 — 실제 계산값**: 왕복/편도 실제 경로탐색 소요시간(Kakao Mobility
   `totalDuration`) + 경유지 대기시간 합 + 도착지 대기시간(왕복이면 최종 목적지까지
   왕복 시간도 포함)을 전부 더해서 8시간(28,800초) 이상이면 즉시 `daily_driver`로 전환.
2. **2순위 — 접수 시 답변한 시간구간**: 1순위 값을 계산할 수 없는 경우(주소 좌표
   미해결, 경로탐색 실패 등) — §7-1에서 사용자가 답한 시간구간이 "8시간 이상"이면
   접수 즉시 `daily_driver`로 전환.
3. **3순위 — 관리자 수동 변경**: 위 둘 다 판단 불가한 경우, `premium`으로 접수해두고
   오더 상세 화면에서 관리자가 수동으로 타입을 바꿀 수 있게 한다(기존 "상태 변경"
   패널과 같은 자리에 "오더 타입 변경" 소형 폼 추가).

### 7-3. 프리미엄 구간요금표 (신규 기능, 결정)

탁송의 거리 기반 구간요금표(`fare_rules`/`fare_extra_settings`, `lib/branchPolicy.js`의
`calculateFare`)와 같은 구조를, **프리미엄은 시간 구간 기반**으로 별도로 만든다:

- 신규 테이블(가칭) `premium_fare_rules` — 지사별로 시간구간(예: 4시간 이내/8시간
  이내/8시간 이상, 또는 더 세분화 가능하게 지사가 직접 구간을 정의)마다 요금을 설정.
  탁송의 `fare_rules`가 `tier_seq`/`base_distance_km`로 구간을 나누듯, 여기는
  `tier_seq`/`base_hours`로 나눈다.
- 관리자 설정 화면: 기존 지사 탭 구조(`views/branches/fare_rules.ejs`와 형제격)에
  "프리미엄 요금표" 탭 신설.
- `lib/branchPolicy.js`에 `calculatePremiumFare(branchId, hoursBracket)` 추가 —
  `calculateFare`와 같은 반올림/최대값 처리 패턴 재사용.
- AI 챗봇 접수 흐름에서 §7-1의 시간구간 답변(또는 §7-2 1순위의 실제 계산 소요시간)이
  확정되면 이 함수로 자동 요금을 채운다(탁송의 `fare-preview` 라우트와 같은 패턴 —
  `GET /orders/premium-fare-preview?branch_id=&hours_bracket=` 신설 제안).

## 8. 프롬프트 분리 (결정)

`lib/hybridChat.js`의 `buildSystemInstruction()`을 intent별로 나눈다:
- 탁송(`dispatch_order`) — 기존 프롬프트 그대로, 원문 그대로 옮기는 메모 규칙 유지.
- 프리미엄/일일기사(`premium_order`/`daily_driver_order`) — 새 전용 지시문. §2/§4/§5/§6/
  §7-1의 필드·질문 규칙과 요약형 메모 규칙을 반영.

세 intent 모두 값 추출 스키마(`RESPONSE_SCHEMA`)는 공유하되, 일일기사/프리미엄 전용
필드(tripType, waypoints 배열, waitMinutes류, finalDestinationAddress,
reservationHoursBracket)를 추가한다.

## 9. DB 스키마 변경 (결정: 정식 컬럼)

`orders`:
- `order_type` TEXT — `dispatch`/`premium`/`daily_driver`, 기존 데이터는 `dispatch`로
  일괄 채움(하위호환).
- `trip_type` TEXT NULL — `round_trip`/`one_way` (일일기사 전용, 그 외 NULL).
- `final_destination_address` / `final_destination_address_detail` TEXT NULL — 왕복
  일일기사 전용. 기존 `destination_address`는 "1차 도착지"로 그대로 쓴다(경유지 취급
  변경 없음 — 컬럼명 재해석 없이 새 컬럼만 추가하는 쪽이 안전).
- `destination_wait_minutes` INTEGER NULL.
- `reservation_hours_bracket` TEXT NULL — `within_4h`/`within_8h`/`over_8h` (프리미엄
  전용, §7-1/§7-2에서 사용).

`order_waypoints`:
- `wait_minutes` INTEGER NULL — 경유지별 대기시간(§4).

신규 테이블 `premium_fare_rules` — §7-3 참고, `fare_rules`와 동일한 컬럼 패턴에
`base_distance_km` 대신 `base_hours`.

## 10. 경유지 다중 수집 (챗봇 스키마 확장)

Gemini `RESPONSE_SCHEMA`의 `waypointAddress` 등 스칼라 필드는 그대로 두되(탁송 호환
유지), 일일기사/프리미엄 전용 흐름에서는 **클라이언트 FSM 상태(`ai-intake` 쪽)가
경유지를 배열로 누적**한다 — "추가할까요?" 루프 한 번마다 한 개씩 받아서 배열에 쌓는
방식(§4). Gemini 응답 스키마 자체를 배열로 바꾸지 않는 이유: 다른 intent들의 파싱
안정성에 영향을 주지 않기 위함(v1에서 제안한 방식 그대로 채택).

## 11. 구현 순서 제안

1. DB 마이그레이션(§9) — 컬럼/테이블 추가, 기존 오더 `order_type='dispatch'` 백필.
2. `lib/branchPolicy.js`에 `calculatePremiumFare` 추가 + 지사 설정 화면(§7-3).
3. `lib/hybridChat.js` 프롬프트 분리(§8) + 스키마 확장.
4. `public/js/ai-intake.js`(또는 분리된 ai-intake-flow.js/state.js) FSM을 intent별
   분기 — 일일기사/프리미엄 전용 상태(경유지 반복 수집, 2단계 대기시간 질문, 왕복/편도,
   최종목적지) 추가.
5. `routes/orders.js` — 접수 시점 `order_type`/신규 필드 저장, §7-2 자동승격 판정 로직,
   프리미엄 요금 미리보기 라우트.
6. 오더 상세/수정 화면(`OrderForm.js`, `OrderSidePanel.js` 등) — 새 필드 표시/수정,
   관리자용 "오더 타입 변경" 폼(§7-2 3순위).
