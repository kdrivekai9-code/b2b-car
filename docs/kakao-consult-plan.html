카카오 상담톡 연동 — Zammad → b2b-car 챗봇 전환

ConsulTalk 중계서버(consultalk-alpha.callmaner.com)를 통해 들어오는 카카오 상담톡 대화를 현재는 Zammad가 처리하고 있다. 이 문서는 그 처리 주체를 b2b-car 자체 챗봇(하이브리드 분류기 + 배차 주문 도우미)으로 교체하기 위한 구조 분석과 실행 계획을 정리한다.

01

개요

지금 카카오톡 상담톡으로 들어오는 고객 문의는 ConsulTalk 중계서버가 받아서 Zammad(헬프데스크)로 전달하고, Zammad 상담원(또는 Zammad 쪽 봇)이 답장하면 다시 중계서버를 거쳐 고객에게 전달되는 구조로 되어 있다. 이 문서가 제안하는 변경은 딱 하나다 — Zammad가 있던 자리를 b2b-car로 옮긴다. 중계서버와 카카오 쪽 프로토콜은 그대로 두고, "누가 대화를 처리하는가"만 바꾸는 것이므로 카카오 API 자체를 직접 다룰 필요는 없다(중계서버가 그 부분을 이미 흡수하고 있음).

b2b-car는 이미 웹 챗위젯용으로 lib/hybridChat.js(의도분류·필드추출)와 lib/mcpDispatchAgent.js(주문조회·변경 도구 실행)를 갖고 있다. 이 문서의 핵심은 이 두 모듈을 그대로 재사용하면서, 지금까지 없던 "로그인하지 않은 카카오 고객"이라는 새로운 진입 경로를 어떻게 안전하게 열 것인가에 있다.

ConsulTalk의 zammad_send_message / zammad_upload_file / zammad_send_close 세 엔드포인트는 전부 Zammad → 중계서버 방향(Zammad의 웹훅이 호출하는 자리)이다. 안에서 바디로 받은 user_key/service_key/event_key를 헤더 형식(X-User-Key 등)으로 바꿔 기존 /send/* 엔드포인트를 그대로 호출하는, "Zammad 전용 얇은 래퍼"다. 반대로 고객 → Zammad 방향(수신 쪽)이 실제로 어떻게 Zammad에 꽂혀 있는지는 이 API 문서에 노출되어 있지 않다 — 중계서버 내부 설정이거나 별도 연동일 가능성이 높다.

03

중계서버(ConsulTalk) API 정리

consultalk-alpha.callmaner.com/openapi.json 기준으로 확인한 전체 엔드포인트다. b2b-car가 직접 쓸 것과 Zammad 전용(교체 대상)을 구분해뒀다.

발신 (b2b-car → 고객)

엔드포인트용도구분
POST /send/message상담사(=b2b-car 봇/상담원)가 고객에게 메시지 전송. 헤더로 인증(X-Service-Key/X-User-Key/X-Event-Key)직접 사용

⚠ 확인 필요

이 6개 수신 엔드포인트는 "카카오 → 중계서버" 방향이지 "중계서버 → b2b-car" 방향이 아니다. 즉 이 문서에 있는 API만으로는 중계서버가 받은 걸 우리 쪽으로 어떻게 다시 보내줄지 알 수 없다 — 지금 Zammad로 가는 경로가 중계서버 내부 하드코딩인지, service_key별 웹훅 URL 설정인지부터 확인해야 한다. 8절 참고.

04

카카오 상담톡 원본 스펙 — "상담톡 API (DKT) v1.2" 확인 사항

중계서버가 감싸고 있는 원본 규격 문서(상담톡 API (DKT) v1.2, 25.03.25)를 확인했다. (카카오 쪽에 v1.4(26.4.8, 51페이지) 최신본이 별도로 존재하지만, 지금 연동 대상인 ConsulTalk 중계서버 자체가 구버전 스펙 기준으로 만들어져 있어 이번 계획서는 의도적으로 v1.2를 기준으로 삼는다 — 중계서버가 v1.4에 맞춰 갱신되면 그때 이 섹션도 다시 검토한다.) 엔드포인트 경로(/api/v1/send/message, /api/v1/receive/reference 등)와 헤더(X-Platform-Type/X-Service-Key/X-User-Key/ X-Event-Key)가 ConsulTalk 스펙과 완전히 동일하다 — 즉 ConsulTalk은 이 DKT 규격을 그대로 구현한 것이고, 3절의 /send/*· /receive/* 엔드포인트는 이 문서가 정의하는 "BZM"(카카오 비즈메시지) 연동 규격 그 자체다. 아래는 3절에 없던, 실제 설계에 영향을 주는 세부 규칙이다.

4.1 상담 세션 라이프사이클

구분조건
생성고객이 "상담 연결하기"로 상담 요청
고객이 카카오톡 채널 채팅방에 직접 메시지 전송
유지마지막 메시지 수신 후 30일간 유지 — 고객 메시지가 올 때마다 연장
종료상담원이 상담 종료
상담원이 카카오톡 사용자를 차단
고객이 채팅방에 "!종료" 입력(플랫폼 예약 커맨드)
고객이 채팅방 나가기 / 채널 차단
마지막 메시지 수신 후 30일 경과(자동 만료 → /receive/expired_session)

"!종료"는 우리 쪽이 처리하는 게 아니라 플랫폼이 가로채는 예약어다 — b2b-car 봇이 별도로 이 문구를 감지할 필요는 없고, 세션이 끝났다는 사실만 /receive/expired_session(또는 별도 종료 통지가 있다면 그쪽)으로 통지받는다.

4.2 UserKey의 특성 — DB 설계에 직접 영향

  • 카카오톡 채널별로 다르다 — 같은 사람이라도 채널(지사?)이 다르면 다른 UserKey.
  • 대소문자를 구분한다.
  • 채널을 차단했다가 해제해도 UserKey는 안 바뀐다.
  • 카카오톡 탈퇴 후 재가입하면 UserKey가 바뀐다.
⚠ 설계 반영

마지막 항목 때문에 external_user_key만으로는 고객을 영구히 식별할 수 없다 — "탈퇴 후 재가입"이 흔한 일은 아니지만, 등록 고객 매칭(5.1)은 UserKey가 아니라 전화번호(personal_info 동의로 수신)를 1차 식별자로 삼고, UserKey는 "같은 세션 내에서 재진입을 빠르게 찾기 위한 보조키" 정도로만 쓰는 게 안전하다.

4.3 "상담원" = 반드시 사람이 아님, 과금 단위

문서가 명시적으로 정의한다: "상담원은 카카오에서 제공하는 상담톡 API를 이용하는 주체를 의미하며 반드시 사람을 지칭하는 것은 아니다." 카카오 쪽에서는 실제 사람이 배정됐는지 봇이 자동응답 중인지 구분하지 않는다. 그리고 항목 선택 등 자동 발신도 상담원 발송(과금 대상)으로 잡힌다 — 오직 "시스템 메시지"(4.5의 platform_answer)만 과금에서 빠진다. b2b-car 봇이 자동으로 보내는 답장도 전부 과금 대상 메시지라는 뜻이므로, 예상 메시지량 기준 비용을 10절(리스크)에서 함께 짚는다.

4.4 메시지 보관 정책 — 우리 쪽 로그가 유일한 영구 기록

상담 메시지는 상담톡 시스템 자체에는 저장되지 않고, 카카오톡 메시지 시스템에 3일간만 보관된다. 챗봇 대화 이력 조회(/send/chatbot)도 "상담 시작 시점 기준 최근 3일"까지만 가능하다. 즉 b2b-car가 chat_messages에 저장하는 사본이 3일이 지나면 유일하게 남는 기록이 된다 — 7절의 kakao_consult_events 감사로그를 "있으면 좋은 것"이 아니라 "이것 없으면 3일 후 복구 불가"로 필수 취급해야 한다.

4.5 메시지 타입 카탈로그

발신(/send/message, /send/plain)이 지원하는 chapters[].sections[] 구성이다.

b2b-car의 chat_messages.message는 순수 텍스트 컬럼이라, 1차 범위는 SimpleText만으로 좁히는 5.7의 결정을 유지한다. 다만 platform_answer (시스템 메시지, 과금 제외)는 운영시간 외 자동안내에 유용해 1차 범위에 포함시킬 것을 제안한다.

4.6 /receive/reference(상담원 연결) 실제 필드

원본 스펙은 ConsulTalk이 노출한 것보다 훨씬 풍부하다 — user_key/session_id/ sender_key/app_user_id/time 외에 reference.text(상담원 연결 버튼을 누르기 직전 고객이 입력한 문구), reference.lastText/lastTextDate(가장 최근 대화), last_reference.bot/bot_event(직전에 어떤 봇 시나리오였는지)까지 온다. 6.5(상담원 전환) 설계에서 이 reference.text를 상담원 카드보드에 "고객이 방금 뭐라고 했는지" 요약으로 바로 보여주면 인계 품질이 좋아진다.

4.7 /receive/message 원본 필드 vs ConsulTalk 래핑

원본 스펙의 수신 바디는 user_key/session_id/sender_key/ time/serial_number/content/contents(배열)/ type로 비교적 단순하다. ConsulTalk이 이걸 chapters[].sections[] 구조로 한번 더 감싸서 노출하고 있다는 뜻이므로, b2b-car는 ConsulTalk 스펙(3절)만 상대하면 되고 이 원본 구조를 직접 파싱할 일은 없다 — 참고용으로만 남긴다.

✓ seen_info / personal_info — DKT 원본에 없는 이유 확인

원본 스펙(v1.2, 25.03.25, 총 23페이지)의 Receive Service API는 /reference, /message, /expired_session 3개뿐이다 — seen_info, personal_info는 이 문서 자체에 항목이 없다. ConsulTalk의 실제 배포 서버 (/openapi.json)를 직접 조회해 확인한 결과, 두 엔드포인트는 실재하며 코드 docstring에 "명세서 IF11004"처럼 더 상세한 카카오 부록/버전 문서(IF 번호 체계)를 근거로 인용하고 있다 — 즉 우리가 받은 23페이지 문서는 DKT 스펙의 축약본이고, 이 두 엔드포인트는 그 부록에만 있는 항목으로 보인다.

seen_info 요청 바디는 ConsulTalk 서버에서 실제로 확인됐다: { user_key: string, session_id: string|number, sender_key: string, time: number } — 고객이 채팅방을 읽은 시각을 전달하는 용도이며, ConsulTalk 자체 문서에 "과거 미구현 시 카카오가 404로 재시도를 유발했다"는 경고가 남아있어 필수 구현 항목으로 확정한다.

personal_info는 여전히 필드 스펙이 없다 — ConsulTalk 서버조차 이 엔드포인트를 타입 검증 없이 원시 바디로 받고 있어(Pydantic 스키마 미정의), "닉네임/전화번호 등" 설명 외의 정확한 필드명은 카카오 부록 문서나 callmaner 쪽 실제 수신 로그 샘플을 받아야 확정할 수 있다.

    B->>B: kakao_chat_sessions에서 세션 찾기/생성
    B->>G: classifyAndExtract(text)
    alt 주문 조회/변경 의도
        B->>M: runDispatchAgent(ctx, text)
        M-->>B: 처리 결과 텍스트
    else FAQ/오더접수
        G-->>B: 분류 결과
    end
    B->>R: POST /send/message (X-Service/User/Event-Key)
    R->>K: 카카오 발신 API
    K->>C: 답장 전달

    C->>K: "상담원 연결" 버튼
    K->>R: POST /receive/reference
    R->>B: POST /kakao-consult/receive-reference

06

상세 설계

5.1 고객 식별 모델 — 가장 중요한 결정

b2b-car의 chat_sessions는 user_id → users(id)가 필수라 로그인 계정이 없으면 세션 자체를 못 만든다. 카카오 상담톡 고객은 b2b-car 계정이 없는 게 기본값이므로, 다음 두 경로를 병행한다.

  • 등록된 고객 — 카카오 발신 전화번호(personal_info 동의로 수신)가 기존 orders.origin_contact/destination_contact와 일치하면, 그 오더가 속한 지사/고객사로 조회 범위를 한정해 자기 오더만 조회·문의할 수 있게 한다(MCP 도우미의 mcp_customer_links 패턴과 동일한 사고방식).
  • 미등록/익명 고객 — FAQ 답변과 신규 탁송 문의(요금 안내 등)까지만 처리하고, 주문 조회·변경류는 상담원 연결로 넘긴다.

이를 위해 chat_sessions.user_id를 nullable로 바꾸고 channel(web/kakao), external_user_key(카카오 userKey), external_phone 컬럼을 추가하는 안을 제안한다(7절).

5.2 수신 웹훅

POST /kakao-consult/receive(신규, 공개 라우트) 하나로 /receive/message와 /receive/message-simple 두 포맷을 모두 받는다. 인증은 세션 쿠키가 아니라 공유 시크릿(중계서버가 보내는 X-Service-Key를 화이트리스트와 대조, 또는 별도 웹훅 시크릿 헤더)으로 한다 — middleware/auth.js의 requireAuth는 이 라우트에 적용하지 않는다.

chapters[].sections[] 구조에서 type: "text" 섹션의 data를 이어붙여 평문으로 만든 뒤 hybridChat.js에 그대로 넘긴다(이 모듈은 이미 세션/DB에 의존하지 않는 순수 함수라 그대로 재사용 가능 — 별도 수정 불필요).

5.3 챗봇 처리 — 기존 모듈 재사용

classifyAndExtract/classifyPhaseReply는 이미 세션과 무관한 순수 함수라 그대로 쓴다. runDispatchAgent는 users 테이블 row(id/name/phone/ branch_id)를 요구하므로, 등록된 고객 케이스에서는 전화번호로 매칭되는 내부 계정을 찾아 그 row를 넘기고, 매칭되는 계정이 없으면 이 도우미는 건너뛰고 FAQ/일반 응답으로만 처리한다.

5.4 발신 연동

답장은 /send/message(또는 파일이면 /send/upload → /send/plain)를 직접 호출한다. 세션별 X-Service-Key/X-User-Key/X-Event-Key를 kakao_chat_sessions에 저장해두고 매 발신마다 재사용한다.

5.5 상담원 전환

/receive/reference 수신 시 기존 chat_sessions.status = 'needs_agent' + notify()(lib/push.js) 흐름을 그대로 태운다. 카카오 쪽에 "상담사를 연결중입니다" 안내만 /send/message로 즉시 응답하면, 이후 흐름은 지금 상담원 카드보드 화면(/chat/sessions)과 완전히 동일하다 — 새로 만들 UI가 없다.

단, 기존 POST /chat/sessions/:id/reply(상담원 답장)에 "이 세션이 카카오 출신이면 /send/message도 같이 호출" 분기를 추가해야 한다 — 지금은 웹 위젯에만 반영되고 끝난다.

5.6 세션 종료/만료

/receive/expired_session → chat_sessions.status = 'closed'. 상담원이 /chat/sessions/:id/close를 누르면 반대로 /send/close를 호출해 카카오 쪽에도 종료를 알린다.

5.7 메시지 포맷 변환

chat_messages.message는 현재 순수 텍스트 컬럼이다. 이미지/파일 첨부는 스키마에 없으므로, 1차 범위는 텍스트만으로 좁히고(사진 문의는 상담원 연결로 유도), 이후 필요하면 attachment_url/attachment_type 컬럼을 추가하는 2차 작업으로 분리한다.

08

확인 필요 사항

ConsulTalk의 공개 API 스펙, 카카오 상담톡 원본 스펙(DKT v1.2), b2b-car 코드베이스까지 확인했다. 아래는 그럼에도 실제 착수 전 반드시 확인해야 하는 것들이다.

8.1 중계서버 다운스트림 설정

중계서버가 /receive/*로 받은 걸 Zammad로 넘기는 방식(고정 URL 하드코딩인지, service_key별 웹훅 URL 설정인지)을 callmaner 쪽(ConsulTalk 운영 담당, 콜마너 연동문서의 정경석 등)에 확인해야 한다. 우리가 직접 못 바꾸는 설정이면 그쪽에 웹훅 URL 변경을 요청하는 절차가 별도로 필요하다.

8.2 서비스 키 발급/개수

X-Service-Key/X-User-Key/X-Event-Key가 지사(branch)별인지 전사 공통 1개인지, 카카오 플러스친구 채널이 지사별로 분리되어 있는지 확인 필요 — b2b-car는 지사 단위로 운영되므로(콜마너 연동도 지사별 callmaner_provider_id) 구조가 다르면 branches 테이블에 관련 컬럼을 추가해야 한다.

8.3 seen_info — 해결됨 / personal_info — 필드 여전히 미확정

seen_info는 ConsulTalk 서버(/openapi.json)를 직접 조회해 실제 바디를 확인했다: { user_key, session_id, sender_key, time }. 이번에 읽은 카카오 원본 스펙(DKT v1.2, 25.03.25, 23페이지)의 Receive Service API에는 이 두 엔드포인트가 아예 없는데 (4절 참고), ConsulTalk 코드는 "명세서 IF11004"를 근거로 인용하고 있어 우리가 받은 문서가 축약본이고 별도 IF 번호 체계의 부록에 정의돼 있는 것으로 보인다.

personal_info는 ConsulTalk 서버 자체가 타입 검증 없이 원시 바디를 받고 있어(설명은 "닉네임/전화번호 등"뿐) 정확한 필드명은 여전히 미확정이다. Drive에 부록 문서가 더 있는지 확인하거나, 안 되면 callmaner 쪽에 실제 수신 로그 샘플 1건을 요청하는 편이 더 빠르다.

8.4 재시도 정책

seen_info 설명에 "과거 미구현으로 404를 반환해 카카오 측 재시도를 유발했음"이라고 명시되어 있다 — 신규 웹훅은 어떤 이벤트든 우선 200을 즉시 반환하고, 무거운 처리(Gemini 호출 등)는 비동기로 넘기는 구조가 안전하다.

실행 계획

0단계

확인 & 접근 확보

8절의 확인 필요 사항을 callmaner 쪽과 조율. seen_info/personal_info 실제 필드가 담긴 문서(있다면)를 Drive에서 추가 확보. 테스트용 서비스 키 발급.

1단계

스키마 & 웹훅 뼈대

7절 DB 변경 마이그레이션 작성. POST /kakao-consult/receive 라우트 신설(공유 시크릿 검증만, 즉시 200 응답 + 로그 적재).

2단계

수신 → 챗봇 연결

텍스트 추출 → classifyAndExtract 연결. FAQ/탁송요금 문의 등 익명 고객도 가능한 범위부터 먼저 응답 흐름 완성 (/send/message 발신 포함).

3단계

등록 고객 & MCP 도우미

전화번호 매칭 로직, runDispatchAgent 연결. 주문 조회/변경까지 카카오에서 가능하게.

4단계

상담원 전환 & 종료

/receive/reference·/receive/expired_session 연결, 기존 상담원 카드보드에서 카카오 세션도 답장 가능하도록 /chat/sessions/:id/reply 확장.

5단계

Zammad 병행 운영 → 전환

일부 지사/채널만 먼저 b2b-car로 전환해 실사용 검증 후, 문제 없으면 중계서버 다운스트림을 전체 전환하고 Zammad 전용 엔드포인트 의존을 제거.

10

리스크 & 고려사항

  • 중계서버 제어권 — 다운스트림 전환이 우리 권한 밖이면 전체 일정이 callmaner 쪽 대응 속도에 종속된다.
  • 익명 고객 오남용 — 로그인 없는 채널이라 요금 문의 남용/스팸에 대한 레이트리밋이 웹 위젯보다 더 필요하다(SESSION_CREATE_LIMIT 패턴을 external_user_key 기준으로 적용).
  • 개인정보 처리 — personal_info 수신 내용은 문서 자체가 "로그에 남기지 말 것"을 명시 — kakao_consult_events 감사로그 저장 시 이 필드는 마스킹/제외 해야 한다.
  • 이중 처리 방지 — Zammad와 b2b-car가 같은 채널을 동시에 구독하면 고객에게 응답이 두 번 갈 수 있다 — 5단계 병행 운영 구간은 반드시 서비스 키 단위로 분리한다.
  • 메시지 발신 = 과금 단위 — 4.3에서 확인했듯 봇 자동응답도 전부 "상담원 발신"으로 과금된다(platform_answer 시스템 메시지만 예외). Gemini 분류가 애매해서 여러 번 되묻는 대화가 늘어나면 비용도 같이 늘어난다 — 웹 위젯 대비 메시지당 비용이 실제로 드는 채널이라는 점을 트래픽 추정에 반영해야 한다.
  • UserKey 비영속성 — 4.2에서 확인했듯 고객이 카카오톡을 탈퇴 후 재가입하면 UserKey가 바뀐다. 등록 고객 식별을 UserKey에만 의존하면 안 되고 전화번호 매칭을 항상 병행해야 한다.
  • 3일 메시지 보관 한계 — 4.4에서 확인했듯 카카오 쪽 원본은 3일이 지나면 사라진다. kakao_consult_events 감사로그가 곧 유일한 영구 기록이므로, 이 로그 자체의 백업/보존 정책을 별도로 정해야 한다.
