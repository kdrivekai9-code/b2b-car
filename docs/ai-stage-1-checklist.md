달리 라우트 자체가 `requireRole('admin', 'branch_manager')`로 막혀 있어 client 역할은
데이터 스코핑이 아니라 아예 403을 받는다 — 이 차이를 그대로 재현했는지가 이번 슬라이스의

- 구현: `src/app/inquiries/page.js`(`NEXT_STAGE1_INQUIRIES_ENABLED` 플래그)가
  `routes/inquiries.js`에서 추출한 `buildInquiriesListData()`를
  `GET /inquiries/data.json`으로 호출. 이 라우트에도 동일한
  `requireRole('admin','branch_manager')`를 적용해서, client 역할이 요청하면 JSON이
  아니라 EJS와 동일한 HTML 403(`views/403.ejs`)을 그대로 받는다 — React 페이지는
  `res.status === 403`을 감지해 같은 안내문을 인라인으로 재현한다(요청 자체를
  API 계약 차원에서 바꾸지 않음). 페이지네이션 없이 `LIMIT 300`으로 캡핑하는 기존
  동작도 그대로 유지했다(계약 변경 없음).
- 검증 방법: 대시보드/오더 목록과 동일 — 임시 Preview 배포(테스트 후 삭제) + 운영과
  동일 `DATABASE_URL` + qa_test_bot(admin) 계정으로 로컬 EJS와 Preview React를
  Playwright로 나란히 비교.
- [x] 페이지 응답 코드 200 확인 — 문의 목록(`/inquiries`)만 해당, admin 기준
- [x] 필터 파라미터 동작 확인 — 문의 목록만 해당
  - [x] 카테고리 필터 — `category=fare` 결과(28건 전부, 데이터 특성상 필터링 효과가

  - [x] 상태 필터(2026-08-01 추가 검증) — `status=new` 결과(28건 전부 — 현재 운영
        데이터가 전부 `new` 상태라 필터링 효과는 안 보였지만, 그 결과 자체가
        EJS/React 완전히 일치)
  - [x] 검색어 필터(2026-08-01 추가 검증) — `q=제주` 결과(2건, ID 리스트까지)가
        EJS/React 완전히 일치
- [x] 무필터 조회 결과(28건 ID 목록) EJS/React 완전 일치 확인(간접적으로 정렬 동일성도 확인)
- [x] 숫자/배지 표기 동일성 확인 — 배편(페리 구간) 필요/없음 배지 색상(red/green)이
      React 페이지에도 동일하게 재현되어 있고, 스크린샷 대조로 실제 렌더링까지 확인
- [x] 권한별 노출 확인 — admin만: 정상 데이터 노출 확인

      정상 접근(자기 지사 스코프 문의 목록 노출), `qa_test_client`는 EJS/React 둘 다

      EJS는 실제 HTTP 403을 응답하는데, React 버전은 Server Component 안에서 403 안내를
      직접 렌더링하는 방식이라 실제 응답 코드는 200으로 나간다(화면 내용은 동일, 상태
      코드만 다름). 사용자에게 보이는 화면은 같지만, 상태 코드에 의존하는 모니터링/외부
      도구가 있다면 이 차이를 감안해야 한다 — 필요하면 Next.js의 `forbidden()`/
      `unauthorized()`(experimental) API로 다음에 맞출 수 있다.

  `DATABASE_URL` + qa_test_bot(admin) 계정으로 로컬 EJS와 Preview React를 Playwright로
  나란히 비교.
