# 핸들모빌리티 상담 로그 기반 — b2b-car 챗봇 응대 현황 재점검

- 작성일: 2026-08-13
- 갱신: 2026-08-13 (같은 날 오후 작업분 반영 — 3절 0)·1)번 해소, 아래 0-1절 참고)
- 대상 로그: 핸들모빌리티 탁송 상담톡, 2024-04-22 ~ 2026-08-06 (494일 / 메시지 약 10,551건 / 요청 1,206건)
- 선행 문서: `docs/kakao-chatbot-upgrade-plan.html` (2026-08-07, 같은 로그를 표본으로 삼은 원 설계 기획서)

## 0. 이 문서의 성격

이 로그는 새로 받은 자료가 아니라, b2b-car 카카오 상담톡 자동화 설계 자체의 근거 데이터였다. 즉 이번 작업은
"처음 보는 데이터로 새 기획을 짜는 것"이 아니라 **원 기획서가 세운 목표 대비 지금 무엇이 실제로 구현됐고,
무엇이 아직 안 됐는지를 다시 확인하는 것**이다. 이미 이번 세션에서 실사용 버그로 발견·수정한 항목은
다시 검증하지 않았다:

- "즉시" 예약 처리 정확성 / 동의어 확장
- 도착지 인도시간 기준 예약, 출발지 픽업시간 질문 즉답
- 질문을 필드 수정 요청으로 오인하던 문제(matchFieldKeyword)
- 책임보험 FAQ 문맥 인식
- 법인 내 동료 간 접수 현황 공유("팀 접수 현황 안내")
- 봇 메시지 중복 저장
- 동일 지명(사당역 등) 완전일치 자동 선택
- MCP 배차 도우미 오라우팅("탁송예약"이 MCP로 새던 문제)

방법: 로그 전체(30,214줄)를 처음부터 끝까지 읽어 새로운 요청 유형을 추출한 뒤, 각 유형과 원 기획서의
Phase 1~4 항목을 실제 코드(`lib/`, `routes/`)와 대조해 구현 여부를 확인했다.

## 1. 원 기획서 Phase별 구현 현황

### Phase 1 — 접수 자동화 (목표: 필수 4종 추출 95%+, 오등록 0건)

**목표를 이미 넘겨 있다.** 폼 파서(룰 우선 + LLM 폴백), 확인 카드, 콜마너 등록, 접수번호 회신,
복수 차량 분해, 단순 응대 무시 규칙 모두 구현·실사용 검증됐다.

현재 파서를 실제 로그 전체에 재생해 측정했다(로그에서 접수 폼 1,428건 추출 → `parseKakaoIntake`
실행). 원 기획서의 97.4%는 전처리된 다른 표본 기준이라 수치가 직접 비교되지는 않는다.

| 결과 | 건수 (측정 시점) |
|---|---|
| 필수 4종 완전 추출 | 1,401건 (98.1%) |
| 폼은 인식했으나 필드 부족 | 12건 (0.8%) |
| 폼 인식 자체 실패 | 15건 (1.1%) |

> 위 수치는 **이 문서 작성 시점(수정 적용 전)** 기준이다. 이후 `8736cb1`(파서 결함 3건, +10건)과
> `e71ac4f`(■ 3장소 폼·도착지 우선 폼, +4건)이 적용되어 완전 추출은 1,415건 = **99.1%**가 된다
> — 단 이 값은 두 커밋이 각각 값 수준 대조로 보고한 증분을 합산한 것이고, 합산 후 로그 전체를
> 다시 재생해 재측정한 값은 아니다(재생 스크립트와 원본 로그가 저장소 밖에 있다).

**실패 1.9%(27건)의 실제 내용 — 전수 분류(수정 전 기준):**

| 사유 | 건수 | 성격 |
|---|---|---|
| `출발지]` — 여는 대괄호 누락 오타 | 9 | **파서 결함**(아래 3-A) |
| 차량번호를 아예 안 적음 / 차종만 적음("차량번호 : 코란도") | 6 | 고객 미기재 — 되묻기가 정답 |
| `■ 출발지` 초기 폼(키수령지가 따로 있는 3장소 구조) | 3 | 스키마 미지원 — 상담원 인계가 정답 |
| 번호판 자릿수 오타("219누863", "8083692") | 2 | 고객 오타 — 되묻기가 정답 |
| 라벨에 공백("주  소:")이 있어 주소 값에 라벨이 섞임 | 3 | **파서 결함**(아래 3-B, 위 9건과 일부 중복) |
| 차종명이 주소로 오인되어 번호판 유실("125다9044 니로") | 1 | **파서 결함**(아래 3-C) |
| 도착지 블록을 출발지보다 먼저 씀 | 1 | 드문 예외 |
| `[출발지]`가 줄 중간에 있음(앞에 안내문이 붙음) | 1 | 드문 예외 |
| 접수 폼이 아닌 메시지(추출 오탐) | 1 | 실패 아님 |

**결론: 실패의 약 40%만 파서 결함이고, 나머지는 고객이 필수 정보를 안 적었거나 오타를 낸 경우로
되묻기가 정상 동작이다.** 원 기획서가 "나머지는 되묻기 한 번으로 회수 가능한 수준"이라고 한 판단이
실측으로 맞았다. 즉 남은 1.9%는 대부분 "고쳐야 할 버그"가 아니다.

**별도로 발견한 오파싱**(실패로 집계되지 않지만 값이 틀린 것): 지역명이 붙은 번호판
("경기35바5081", "충북80자1889")에서 지역명이 **차종으로** 들어간다(`type:"경기"`). 로그 전체에서
6건. 번호판도 지역명이 잘린 채 저장된다.

남은 두 가지 미비점은 3절 참고:
- 사고·클레임 인계 키워드가 실제 클레임 표현을 다 못 잡는다
- 정산 구분(매입/판매/지점이동)이 접수 시점에 전혀 분류되지 않는다

### Phase 2 — 능동 통보와 상태 조회 (목표: 배차 통보 커버리지 29.7% → 95%)

**이 문서 작성 시점에는 가장 큰 격차였고, 같은 날 `113cd12`로 구현됐다.**

작성 시점 진단(기록으로 남김): 배차 완료·출발·도착을 감지해 **먼저** 알려주는 스케줄러나 폴링 잡이
없었다. MCP 배차 도우미(`get_my_orders`/`get_eta` 등)로 **고객이 먼저 물어봐야** 답이 나가는
반응형(reactive) 구조뿐이었다.

지금은 매분 크론(`/kakao-consult/cron/order-notifications`, [vercel.json](../vercel.json))이 콜마너
상태 변화를 읽어 카카오·웹챗으로 선제 발신한다(`lib/kakaoOrderNotify.js`). 사건 5종:

| 사건 | 기본 | 기본 지연 | 비고 |
|---|---|---|---|
| `dispatched` 배차완료 | ON | 2분 | 배차 직후 기사 취소가 있어 바로 안 보낸다 |
| `started` 운행시작 | ON | 즉시 | 콜마너 `baecha_status=2`를 처음 쓰기 시작했다 |
| `completed` 운행완료 | ON | 즉시 | |
| `dispatch_cancelled` 배차취소 | ON | 즉시 | "다른 기사님께 배차 진행중" — 사실이고 유용하다 |
| `cancelled` 오더취소 | **OFF** | — | `db93b41` 참고. 콜마너 '취소'는 재배차 전 일시 상태라 오발신이 된다 |

문구·지연·사진첨부는 지사별로 설정한다(`views/branches/customer_notifications.ejs`,
`branch_customer_notifications`). 상태 되돌림 가드(콜마너가 운행 중에도 `status='배차'`를 계속 주는
문제)와 중복 방지(오더+사건+기사 식별값)가 함께 들어가 있다.

⚠️ **다만 배포 후 한동안 실제로는 한 번도 돌지 않았다.** 이 라우터 전체에 걸린 `checkWebhookAuth`가
`X-Webhook-Secret`을 요구하는데 Vercel 크론은 `Authorization: Bearer <CRON_SECRET>`을 보내므로 매분
401로 막혔다(프로덕션 로그 실측: 같은 시각 `/callmaner/sync`는 200). `0921dfa`에서 크론 경로를 그
검증에서 빼 고쳤다 — 크론 라우트는 각자 `CRON_SECRET`을 검사한다. **커버리지 목표(95%) 달성 여부는
이 수정이 배포된 뒤의 실제 발신 로그로 재측정해야 한다.**

같은 커밋에서 폴링 대상도 넓혔다. 예전에는 `status NOT IN ('완료','취소')`로 종료 건을 아예 빼서,
기사 취소로 잠깐 '취소'가 찍힌 오더가 콜마너에서 '접수'로 되살아나도 우리 화면에는 영영 '취소'로
굳었다. 이제 완료·취소도 `updated_at` 기준 60분(`CALLMANER_TERMINAL_RECHECK_MINUTES`) 동안 재조회한다.
되살아나는 전이(취소 → 접수)는 통보를 만들지 않는다 — 화면 상태만 조용히 바로잡힌다.

"기사 연락처 조회"에 대응하는 전용 MCP 도구는 여전히 없지만(`search_place`, `get_my_orders`,
`get_order_history`, `get_fare_quote`, `get_eta`, `create_order`, `update_order`, `raise_fare`,
`cancel_order`), **`get_my_orders` 응답에 이미 실려 나온다** — `summarizeOrders`가 배차된 건에만
`기사명`/`기사연락처`(콜마너 안심번호 050)를 붙이고, 배차 전에는 필드를 아예 넣지 않는다(빈 값을
넣으면 모델이 "연락처가 없습니다"로 단정한다). `scripts/check-driver-contact.js`로 확인했다.
배차완료 통보 기본 문구에도 `{driver_name}`/`{driver_phone}`이 들어 있다.

### Phase 3 — 사진·주행거리 파이프라인 (목표: 사진 자동 첨부 통보 90%+)

**경로는 전부 이어졌다. 남은 것은 지사가 스위치를 켜는 일이다.**

원 기획서 작성 시점(2026-08-07)에는 카카오 이미지 발신 경로 자체가 없다고 명시돼 있었는데, 그 사이
`lib/kakaoConsult.js`에 이미지 업로드(`/image/plain`)와 발신(`sendImages`) 기능이 구현됐다. 이 문서
작성 시점에는 그 기능이 **고객이 물어봤을 때 답하는 반응형 핸들러**(`tryAnswerPhotoRequest`,
`tryAnswerOdometer`)에서만 쓰였고 능동 발신은 없었다.

`113cd12`로 이어붙인 것:

- **이벤트별 사진첨부 스위치**(`attachPhotos`) — 통보에 기사 사진을 함께 보낸다. 토큰이 아니라
  스위치인 이유는 카카오가 이미지를 본문과 별도 섹션으로 보내서 "문구 중간" 위치를 지킬 수 없고,
  일부만 실패할 수 있어 별도 상태가 필요하기 때문이다. 고객 열람을 막아둔 지사
  (`branch_photo_settings.client_can_view`)는 통보로도 나가지 않는다.
- **콜마너 탁송사진**(`ConsPicture`/`picture.do`) 운행전·운행후 링크를 `order_callmaner_photos`에
  저장하고 오더상세에 노출. 기사 업로드 사진(`order_photos`)과는 섞지 않았다.
- **계기판 주행거리 OCR**(`lib/odometerOcr.js` + `generateJsonWithImages`) → `{odometer_start}`,
  `{odometer_end}` 통보 변수. 확신도<0.6·0km·뒤집힌 값·한 건 3000km 초과는 버린다 — 잘못 읽은 숫자를
  통보하는 게 침묵보다 나쁘다.

**단, 다섯 사건 모두 `attachPhotos` 기본값이 `false`다.** 즉 "사진 자동 첨부 통보 90%+"라는 목표는
코드가 아니라 운영 설정에 달려 있는 상태다. 커밋 메시지의 권고대로 콜마너 실응답에서 사진 순서와
"13번째 = 계기판"을 눈으로 확인한 뒤 켜는 것이 남은 일이다.

### Phase 4 — 부가 옵션과 정산

**부분 구현.**

- 책임보험 옵션/FAQ: 구현되어 있고, 이번 세션에서 문맥 인식까지 개선했다.
- 주유("경유 2만원 주유 부탁", 연료 잔량)·서류(등록증/인감증명서 등): 구조화된 필드가 아니라
  자유 텍스트 메모로만 수용된다. 접수 자체는 되지만, 원 설계가 노렸던 "접수 확인 카드에 체크
  항목으로 노출해 현장에서 서류 없음으로 되돌아오는 사고를 막는다"는 효과는 없다.
- 과태료·통행료 사후비용을 오더에 별도 레코드로 추적하는 기능: 존재 여부를 확인하지 못했다.

## 2. 로그에서 새로 확인된 요청 유형 (원 기획서에 없던 것 위주)

원 기획서의 표 2-2/2-5(접수 유형, 접수 외 인텐트)에 없었거나 뭉뚱그려져 있던 패턴 중, 이번에 실제
발화를 다시 훑어 개별적으로 확인한 것들이다.

| 유형 | 실제 예시(발췌) | 현재 처리 가능성 |
|---|---|---|
| 여러 대 동시 접수(2~10대) | "[탁송요청 1]~[탁송요청 3]"으로 5대씩 3세트 | **가능** — 한 폼에 차량 여러 대는 오더 N건으로 분해됨(기존 구현) |

## 3. 수정이 필요한 사항 (우선순위)

### 0) 접수 폼 파서 결함 3건 — ✅ 적용 완료 (`8736cb1`)

아래 셋은 실제 로그 1,428건으로 수정 전/후를 **값 수준까지 대조**해 검증했다(성공→실패 회귀 0건,
값이 달라진 6건은 전부 개선). 적용해 완전 추출률 98.1% → 98.8%가 됐다. 진단 내용은 같은 문제가
재발했을 때 알아보기 위해 그대로 남겨둔다.

**3-A. `출발지]` 여는 대괄호 누락(9건, 실패 원인 1위)**
`ORIGIN_MARK_RE`/`DEST_MARK_RE`가 `[출발지]`·`＊출발지:`·`출발지:`만 받고 `출발지]`는 못 받는다.
고객이 `[`를 빼고 타이핑하는 습관이 2024-10부터 2026-03까지 계속 재발한다 — 오타로 보고 넘기기엔
빈도가 너무 높다. 여는 괄호를 optional(`\[?`)로 바꾸면 9건이 모두 정상 파싱된다(검증 완료).

**3-B. 라벨 안 공백을 못 뗀다(3건)**
`주  소:`, `일  시:`처럼 칸을 맞추려 라벨 안에 공백을 넣는 폼이 있다(2026-03 매입탁송 폼).
`LABEL_RE`가 `주소`를 한 덩어리로만 보기 때문에 라벨이 안 떨어지고, 주소 값이
`"주 소: 강원도 홍천군…"`이 되어 지오코딩이 실패한다. 라벨 글자 사이에 `\s*`를 허용하면 해결.

**3-C. 차량번호 줄 안전장치가 절대 작동하지 않는다(1건 + 잠재)**
`pickVehicles`의 가드가 `if (ADDRESS_HINT_RE.test(line) && !/차량|차종/.test(line))`인데, `line`은
`stripLabel`로 **라벨을 이미 떼어낸** 값이다. 그래서 "이건 차량 줄이다"를 알려줄 `차량번호:` 라벨이
검사 시점엔 사라져 있어, 정작 차량 줄임이 가장 분명한 라벨형 폼에서 이 가드가 한 번도 발동하지
않는다. 차종명이 우연히 주소 패턴과 겹치면(`니로` → `[가-힣]+대?로`) 번호판이 통째로 버려진다.
가드가 원문(`raw`)을 보게 하면 해결. 현재는 "니로" 1건만 걸리지만, `로`로 끝나는 차종이면 언제든 재발한다.

**함께 고쳐야 하는 것 — 지역명 번호판(6건)**: `PLATE_RE`에 지역명 접두어를 허용해야 하나,
`[가-힣]{2}`처럼 아무 두 글자로 열면 **"토레스 150두8774"에서 "레스"를 삼켜 `레스150두8774`라는
없는 번호판을 만든다**(실제로 이 회귀를 만들었다가 값 대조에서 잡았다). 실제 번호판에 쓰이는
광역시·도 이름 17개만 명시적으로 허용해야 안전하다.

> ⚠️→✅ **`■ 출발지` 폼(3건)에 대한 이 문서의 판단은 뒤집혔다** (`e71ac4f`). 원래 판단은 "일부러
> 지원하지 않는 편이 낫다"였다 — 표기만 다른 게 아니라 구조가 달라서다. `■ 키수령지`처럼 출발지·
> 도착지 외 제3의 장소가 있고(키 받는 곳과 차가 있는 곳이 도보 10분 거리), 당시 슬롯 스키마에 담을
> 칸이 없었다. 마커만 추가해 인식시키니 키수령지 주소가 통째로 사라진 채 "성공"으로 등록됐다(실측).
>
> **막힌 지점은 "칸이 없다"가 아니라 "3장소를 어느 칸에 넣을지 규칙이 없다"였다.** 경유지가 접수까지
> 실제로 저장된다는 것(`order_waypoints`)을 확인한 뒤 사용자 확정 규칙으로 풀었다: 키수령지 →
> 출발지(기사가 처음 가는 곳), 원래 출발지 → 경유지(차가 서 있는 곳), 키수령지 상세는 요청사항.
> 키반납지는 경로를 바꾸지 않고 요청사항에만 남긴다(차는 도착지에서 끝나고 키만 걸어가 반납한다).
> 값 수준 대조로 회귀 0건 확인. 즉 "오등록 0건" 요건을 깨지 않고 지원할 수 있었다.

### 1) 능동 배차/출발/도착 통보 파이프라인 — ✅ 구현 완료 (`113cd12`, 크론 인증 후속 수정)
원 기획서의 최우선 목표(배차 통보 커버리지 29.7% → 95%)에 해당하는 파이프라인이 붙었다. 상세는
위 Phase 2 절 참고. **남은 일은 목표 수치의 실측 확인이다** — 크론이 401로 막혀 있던 구간이 있어,
그 수정이 배포된 뒤의 실제 발신 로그로 커버리지를 재측정해야 한다.

### 2) 사고·클레임 인계 키워드가 실제 표현을 다 못 잡는다
`ESCALATION_RE = /(사고|파손|스크래치|기스|찍힘|긁힘|클레임|분실|도난|고장|침수|변상|보상|항의|불만)/`
(routes/kakaoConsult.js)는 로그에 실제로 나온 "부품을 임의로 탈거해서 전달", "연락도 없이 알아서
가셨네요" 같은 표현을 하나도 안 잡는다. 이 경우 봇이 자동 응대 경로로 처리해버릴 위험이 있다 —
사람이 반드시 봐야 하는 유형이 키워드 매칭에만 의존하다 새는 것이다. 키워드 확장만으로는 한계가
있으니, LLM 기반 "이건 사람이 봐야 하는 불만인가" 판정을 보강 검토가 필요하다.

### 3) 접수 후 차량번호 정정을 채팅으로 반영할 수 없다
MCP `update_order` 스키마(`lib/mcpDispatchAgent.js`)에는 `scheduledAt`/`departure`/`arrival`/`fare`/
`notes`만 있고 차량번호 필드가 없다. 시간·주소·요금 변경은 되는데 차량번호 정정만 안 되는 상태라,
실사용에서 반복되는 요청(오타·구형 번호판 교체)이 매번 상담원 인계로 빠진다.

### 4) 사진 첨부 메시지의 내용이 완전히 버려진다
`routes/kakaoConsult.js`의 `describeNonTextMessage`는 이미지 메시지를 "[사진]" 표시만 남기고 **첨부
URL조차 저장하지 않는다**("첨부 URL은 남기지 않는다 — 카카오 첨부 링크는 만료되고..."). 무인 픽업
안내처럼 사진으로 정보를 전달하는 실사용 사례가 있는데, 지금은 그 사진이 대화 이력 어디에도 남지
않아 상담원도 나중에 확인할 방법이 없다. 최소한 만료 전 첨부 URL을 저장하거나, 사진이 포함된 메시지는
자동 응답을 보류하고 사진과 함께 상담원에게 넘기는 처리가 필요하다.

### 5) 정산 구분(매입/판매/지점이동) 필드가 없다
접수 시점에 이 구분을 받거나 저장하는 필드가 전혀 없다. 실제로 정산 담당자가 반복적으로 "구분이
다르게 분류되고 있다"고 지적하는 상황이 로그에 여러 번 나온다. 접수 슬롯에 order_purpose류 필드를
추가하거나, 최소한 메모에 표준 표기로 자동 삽입되도록 하는 보완이 필요하다.

### 6) 특정 기사 지정배차 요청을 반영할 경로가 없다
create_order/update_order 어디에도 기사 지정 파라미터가 없다. 완전 자동 반영은 콜마너 API 지원
여부부터 확인이 필요하지만, 최소한 요청사항(메모)에 "지정기사: 이름/연락처"로 남겨 배차 담당자가
볼 수 있게 하는 정도는 바로 가능하다.

### 7) [낮은 우선순위] FAQ 공백 — 서비스 범위 밖 질문
"캐리어(어부바) 탁송" 같은 질문에 대한 지식베이스 항목이 없다. 코드 변경 없이 지식베이스에 항목만
추가하면 되는 낮은 비용의 개선이다.

## 4. 코드 수정 전에 확인/결정이 필요한 것

- **연휴 접수 정책**: 기존 FAQ는 "됩니다, 당직 근무자가 24시간 운영"이라고 안내하는데, 로그에는 특정
  연휴 기간에 "카톡접수건에 대해서 바로접수가 어려움이 있어 연휴기간에만 대표번호로 접수" 안내가
  실제로 나간 사례가 있다. 실제 정책이 "항상 24시간"인지 "연장 연휴는 예외"인지 확인이 먼저다 —
  확인 전에 FAQ 문구나 코드를 임의로 바꾸지 않았다.
- ~~**`get_my_orders` 응답에 기사 연락처가 실제로 포함되는지**~~ → **확인됐다. 포함된다.**
  `summarizeOrders`(`lib/mcpDispatchAgent.js`)가 배차된 건에만 `기사명`/`기사연락처`를 붙이고, 배차
  전에는 필드를 넣지 않는다. 값은 `orders.callmaner_driver_phone` — 콜마너 안심번호(050)다.
  `scripts/check-driver-contact.js`로 검증되어 있다. 배차완료 통보 기본 문구에도
  `{driver_name}`/`{driver_phone}`이 들어 있으므로, **기사 안심번호를 고객에게 안내하는 것은 이미
  운영 중인 동작이다** — "전용 MCP 도구가 없는 것"이 정책적 차단은 아니었다.
- **기사 실번호(안심번호가 아닌 개인번호)까지 안내해도 되는지**는 여전히 미확인이다. 현재 나가는
  값은 050 안심번호뿐이고, 실번호를 노출하는 경로는 만들지 않았다.

- **`{odometer_start}`/`{odometer_end}`를 통보 문구에 넣기 전 확인**: 콜마너 실응답에서 사진 순서와
  "13번째 = 계기판"(`branches.odometer_photo_index` 기본값)이 맞는지 눈으로 봐야 한다. 잘못 읽은
  주행거리가 고객에게 나가는 것이 침묵보다 나쁘다.

## 5. 챗봇 개선 대상이 아닌 것 (운영/비즈니스 프로세스)

아래는 로그에 반복적으로 나타나지만, AI 챗봇의 자동 응대로 해결할 성격이 아니라 핸들모빌리티 내부
정산·운영 워크플로우에 해당한다:

- 유류비 등 추가비용을 계좌번호와 함께 청구하는 것(상담원의 정산 업무)
- 월 마감 처리 요청
- 과태료·통행료 고지서 사후 처리(외부기관 발행 서류의 사후 정산)
- 경매장(롯데오토옥션/글로비스) 결제 지연으로 인한 출고 거부(외부 시스템 문제)
- 신규 담당자의 법인등록 절차(이미 있는 관리자 기능, AI 챗봇의 접수 응대와는 다른 영역)
